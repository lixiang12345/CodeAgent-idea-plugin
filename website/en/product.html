Product

A project-level coding agent
built for real engineering repositories

CodeAgent is not "a chat box with syntax highlighting". It is an IDE-native agent product: the interaction layer lives inside the JetBrains Platform, context comes from a local retrieval engine, and execution power comes from an approval-gated IDE capability gateway.

Positioning

One sentence, three pillars

CodeAgent is the combination of an IDE-native coding agent, a separately deployed agent backend, a local ContextEngine, and approval-gated IDE capabilities. Remove any pillar and the product falls over.

IDE-native capability gateway

The plugin owns project access, the editor, the terminal, diff and rollback — and puts every change through approval. The agent gets controlled, real capability, not copy-paste suggestions.

Local ContextEngine

An open-source retrieval component indexes your whole repository on your machine: SQLite storage, file watching, five model-free retrieval types. Context quality sets the agent's ceiling — and it all happens locally.

A deployable agent backend

Prompts, model credentials, streamed model calls and tool orchestration are centralized in one deployable backend service: one Docker command locally, or a hosted deployment with OIDC for the whole team.

Why CodeAgent

How it differs from a generic AI chat assistant

Pasting code into a web chat gets you suggestions. An engineering-grade agent needs much more than an answer.

Workflow

Pick a mode by trust level

The three modes share the same threads, context and tool surface — the only difference is what the agent is allowed to do.

AGENT · HANDS-ON

Hand it the whole job

  • Typical tasks: build features, fix bugs, add tests, refactor
  • Plans a task list and loops through tools until done
  • Every file and command change passes an approval card
  • Output lands in Agent Edits for one review pass
CHAT · PAIRING

Discuss with a colleague who knows the repo

  • Typical tasks: design options, walkthroughs, review notes
  • Brings retrieved files and symbols along automatically
  • Attach project files and images as context any time
  • Hand over to Agent mode once the plan is settled
ASK · READ-ONLY

Ask production repos safely

  • Typical tasks: onboarding into unfamiliar code, incident digging
  • Strictly read-only: no file writes, no command execution
  • For repositories with zero tolerance for changes
  • Switch modes only when conclusions hold up
ContextEngine

Context is the agent's ceiling

CodeAgent reuses the open-source ContextEngine as its retrieval layer, pinned as a Git submodule and shipped with the plugin — retrieval quality is measurable and reproducible.

Retrieval typeWhat it solves
LexicalExact matches for identifiers, strings and regex patterns
SymbolLocate definitions and references by function, class or method
PathScope quickly by directory structure and file names
Code graphExpand relevant context along dependencies and call relations
Git lineageCombine commit history to find who changed what, when and why
Semantic (opt-in)Enabled only after you explicitly configure an OpenAI-compatible embedding endpoint and rebuild the index
  • Zero model dependency by default — the first five retrieval types are pure local computation; no local embedding or reranker model is ever installed or started.
  • Incremental sync — after initialization the watcher keeps the index current with adds, changes and deletions; a status chip reports init, sync and watcher failures live.
  • Multi-root workspaces — indexes and activation are managed per root directory.
  • Measurable retrieval — the repository ships a golden-query benchmark and baseline comparison report, so retrieval regressions get caught by CI.
  • MIT licensed — ContextEngine is distributed with the plugin under the MIT license, with transparent provenance.
Separation of Concerns

Who owns what, in one table

Clear responsibility boundaries are the precondition for the security model: each layer holds only the minimum data and privilege its job requires.

LayerResponsibilitiesData held
IDE plugin (JVM) Project access, approvals, editor actions, terminal execution, diff / rollback, managed processes, message queue OIDC tokens and BYOK keys (Password Safe), plugin settings
JCEF frontend (Svelte) Panel interaction: threads, message stream, approval cards, tasks, Git, Image Canvas, Settings UI state; falls back to a Swing UI when JCEF is unavailable
Local sidecar (Node) ContextEngine indexing, file watching, five retrieval types and text search The SQLite index — always on the developer's machine
Agent backend (deployable) Prompt composition, model calls and routing, the bounded tool loop, accounts / subscription / sharing / notifications Model and integration credentials, conversation records — centralized, never pushed to IDEs
Extensibility

Extensible — within boundaries

Every extension mechanism follows the same route: declare, validate, grant explicitly. Capability can grow; the trust model cannot be bypassed.

  • Rules — repository-level guidance injected always-on; team conventions take effect once, for every run.
  • Skills — capability packs selected explicitly per task; validated by the JVM, composed by the backend.
  • Commands & Hooks — custom commands and lifecycle hooks wired into the real run pipeline.
  • Agent profiles & subagents — synchronous / asynchronous subagents with persisted output, cancel, retry and result hand-back.
  • MCP servers — extend the tool surface over the standard protocol, with OAuth metadata discovery and dynamic client registration.
  • Declarative plugins — bounded JSON manifests: source, version, integrity and granted capabilities are validated item by item; no JVM / Node / shell executable code is ever loaded.
Data Flow

Where data goes, in writing

Always local

Your source code, ContextEngine's SQLite index, file-watch events. Analysis relies on retrieval, not on uploading the repository.

Sent per run

The repository context, rules, skills, messages and tool results selected for the current agent run — sent to the one backend you configured.

Backend only

Model API keys, integration credentials, subscription and account data. Rotation, audit and revocation happen in one place, server-side.

Honesty is a product feature. Settings reports real backend health and real model/tool discovery; cloud capabilities like sharing, notifications and subscription clearly state "unavailable, and why" when the backend isn't configured. No interaction ever fakes success.
Deployment

For one developer, or the whole team

The same backend image, two shapes: individual developers run local Docker and go; platform teams host it and centrally govern models, accounts and quotas.

  • Local mode — one docker compose command, service on 127.0.0.1:8788, fresh plugin installs connect with zero configuration.
  • Hosted mode — build the same Dockerfile; configure a unified model gateway or a multi-provider allowlist, PostgreSQL and OIDC login.
  • Accounts & subscription — OIDC single sign-on; plans, usage quotas and warning thresholds counted for real by the backend.
  • Collaboration surfaces — read-only session share links (tokens stored as hashes only; copying rotates the link) and operator notifications.
  • Cloud session recovery — account conversations can be restored from the backend onto a new machine.
