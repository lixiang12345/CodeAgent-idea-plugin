User Manual

Install, configure and get the most out of CodeAgent, from zero. This manual matches plugin v0.7.30; all commands and paths are relative to the repository root.

Quick start

Four steps to a running CodeAgent. The default route uses the local Docker backend — no account, no cloud service required.

  1. Start the local agent backend

    Run one command from the repository root; Docker builds and publishes the service at http://127.0.0.1:8788:

    bash
    docker compose -f backend/compose.yaml up -d --build
  2. Install the plugin

    Open Settings → Plugins → ⚙ → Install Plugin from Disk…, pick the plugin ZIP from build/distributions/, and restart the IDE when prompted.

  3. Open the CodeAgent panel

    Use Tools → Show CodeAgent, or press Ctrl+Alt+I (⌃+⌘+I on macOS). With the local Docker backend running there is no URL or token to enter.

  4. Wait for the index, then send your first task

    ContextEngine initializes the project index automatically; the status chip shows progress. Pick Agent mode, type something like "add failure-path tests for the login endpoint", and watch it work through the approval cards.

A good first task: ask "what is the overall structure of this repository?" in Ask mode — a zero-risk way to feel the retrieval quality before escalating to Chat and Agent.

Install the plugin

From a ZIP

  1. Get the plugin distribution (CodeAgent-*.zip; build output lives in build/distributions/).
  2. Open Settings → Plugins, click the ⚙ icon in the top-right, choose Install Plugin from Disk….
  3. Select the ZIP, confirm, and restart the IDE when prompted.

From source

bash
git submodule update --init --recursive
cd frontend && npm ci && cd ..
cd sidecar && npm ci && cd ..
cd backend && npm ci && cd ..
cd vendor/context-engine && npm ci && cd ../..
./gradlew buildPlugin

The installable ZIP is written to build/distributions/; you can also launch a sandbox IDE with the plugin using ./gradlew runIde.

Deploy the agent backend

The backend owns prompts, model credentials, streamed model calls and tool orchestration. Pick whichever deployment shape fits:

Option 1: local Docker (recommended for individuals)

bash
# Configure backend/.env from backend/.env.example first, then from the repo root:
docker compose -f backend/compose.yaml up -d --build

The service is published at http://127.0.0.1:8788, and fresh plugin installs connect to it automatically — no login, no URL entry.

Option 2: direct development run (no Docker)

bash
cd backend && npm start

This listens on port 8787; you must override the Backend URL in Advanced Settings for the plugin to use it.

Option 3: hosted deployment (teams)

Build the image from backend/Dockerfile, deploy it on your infrastructure, and configure these environment variables (full details in backend/.env.example):

CategoryVariablesPurpose
Models (pick one)MODEL_BASE_URL + MODEL_API_KEYUnified model gateway contract
OPENAI_* / GROK_* / ANTHROPIC_*Fixed multi-provider allowlist

OIDC_ISSUER / OIDC_CLIENT_ID / OIDC_CLIENT_SECRETOIDC single sign-on
PUBLIC_BASE_URL / SESSION_SIGNING_KEYPublic address and session signing key
Optional: sharingSHARE_BASE_URL / SHARE_LINK_TTL_SECONDSRead-only session share links

On the client side: enter the backend URL under Settings → Services, then sign in from Settings → Account via OIDC.

Sharing, notifications and subscription are optional cloud surfaces. While unconfigured, share requests answer 503 with a reason, notifications return an empty list, and subscription state is unknown — the UI reports this honestly instead of pretending availability.

First run

  1. Open the panel

    Tools → Show CodeAgent or Ctrl+Alt+I (⌃+⌘+I on macOS). The panel docks into the IDE's side tool window.

  2. Confirm the backend connection

    The local Docker backend connects automatically; for hosted deployments configure the URL and sign in first. Settings shows real health-check results — a configured URL is not the same as an online backend.

  3. Wait for index initialization

    ContextEngine builds the project index automatically, then watches files and syncs incrementally. The repository status chip shows initialization, auto-sync and watcher failures; clicking it only refreshes or retries after an error.

  4. Pick a mode and start talking

    Switch between Agent / Chat / Ask above the input box. Node.js is discovered automatically; with multi-version setups, point Advanced Settings at a 22.5+ executable.

Interface tour

Top to bottom, the panel has five areas:

  • Top bar — thread title, context usage, zoom, sharing and the thread menu; the hamburger on the left opens the threads drawer.
  • Context row — current workspace (switchable in multi-root projects), the Guidelines entry and the index-sync status chip.
  • Message stream — user messages, streamed assistant replies, tool cards (retrieval / file IO / terminal / Mermaid and more), approval cards and the task list. Tool cards expand to show input and output detail.
  • Changes bar — shows "N files changed" whenever edits exist, with Review / Keep All / Discard All shortcuts.
  • Input area — the message box, mode switcher, model display, attachment / context buttons and send control; it becomes a stop button during a run.

The workspace menu in the top-right opens Tasks, Git and Image Canvas; the settings gear opens the full Settings workspace.

The three modes

ModePermissionsBest for
AgentRead + write + terminal (all approval-gated)Building features, fixing bugs, adding tests, refactoring — delivering a complete change
ChatRead + retrievalDesign discussions, walkthroughs, review feedback — a colleague who knows the repo
AskStrictly read-onlyUnderstanding unfamiliar code, incident digging — zero-risk questions against production repos

Switch modes any time at the bottom-left of the input box, and mix them within one thread: analyze in Ask, settle the plan in Chat, then execute in Agent. Messages typed during an active run join a per-session FIFO queue, dispatched in order by the IDE capability layer without interrupting the current turn.

Managing context

Automatic retrieval

For every run, the backend retrieves relevant code through the local ContextEngine: lexical, symbol, path, code-graph and Git-lineage retrieval are always available and need no model. Retrieved sources and snippets appear as a tool card you can expand and verify.

Manual attachments

  • @ or "+ Context" — attach specific project files to the current message.
  • Drag & drop / paste — drag files in from the project view, or paste text and images directly; pastes over 20 KB warn, over 200 KB are rejected with the actual size.
  • Image Canvas — pick images from a project directory and attach them to the conversation.

Index maintenance

  • The status chip shows initialization / sync / watcher failures; clicking it refreshes, or retries after an error — nothing else.
  • For a full rebuild, run the IDE action CodeAgent: Reindex Context.
  • To audit indexing and sync detail, run CodeAgent: Generate Sync Report.
Semantic retrieval is an explicit opt-in. CodeAgent never installs or starts a local embedding or reranker model; semantic retrieval activates only after you explicitly configure an operator- or organization-hosted OpenAI-compatible endpoint and rebuild the index.

Approvals & permissions

The agent's power is bounded by layered defenses:

  • Approval cards — file writes and terminal commands raise inline approval cards before executing; approve or skip after reading them. Runs waiting for approval are clearly labelled.
  • Per-tool permission rules — configure allow / deny rules per tool in settings (shell commands support input regex); deny rules win.
  • Modes as boundaries — Ask mode forbids all mutations at the capability layer, not by prompt-level convention.
  • Cancel any time — stop a running turn instantly; failed turns support retry and carry a copyable runId for debugging.

Agent Edits & rollback

All file changes from a run are collected in Agent Edits (enter via the Review button on the changes bar):

  • Diff — open each file in IntelliJ's native Diff viewer, identical to manual code review.
  • Undo — revert the agent's edit per file, guarded so it won't clobber your own later manual changes.
  • Keep all / Discard all — accept or drop everything in one click.
  • Checkpoints — pre-run file snapshots you can restore wholesale.
Boundary note: edits made by file tools always have a rollback path, but arbitrary side effects of terminal commands cannot be safely inferred, so "automatic rollback of terminal side effects" is deliberately not offered. Review risky commands carefully at approval time.

Managing threads

  • Threads drawer — open with the top-bar hamburger; search, create and switch.
  • Status at a glance — active runs, pending approvals, failures and unread reply counts show right on list items; unread counts persist.
  • Pin and delete — pin frequent threads; deletion asks for confirmation.
  • Markdown import / export — export conversations for archiving, review or migration; import to continue.
  • Long-conversation navigation — request-by-request jumps plus a jump-to-latest button; tool and approval updates never yank you away from history, and the local read cursor only advances when you actually reach the newest content.
  • Cloud recovery — for hosted accounts, CodeAgent: Recover Conversations from Backend restores your sessions onto this machine.

Tasks · Git · Image Canvas

Tasks

Task lists persist per thread: steps planned by the agent update their status live, you can manage them manually, and Markdown import / export plus clear-completed are built in.

Git

The Git page reads the real index and working tree: stage / unstage, view diffs with JetBrains Diff, and commit only after explicit confirmation — there is no "oops, it committed".

Image Canvas

Preview bounded raster assets from a directory you choose inside the project, and attach images to the current conversation — for example, hand the agent a design mock to implement against.

Mermaid

Mermaid diagrams in assistant output render directly in the panel — great for having the agent explain flows and structures visually.

Rules & Skills

Workspace guidelines

AGENTS.md at the repository root is the workspace-level guidance file, composed into every run's prompt by the backend. Open it quickly with CodeAgent: Edit Workspace Guidelines, or via the Guidelines entry in the panel's context row.

Rules

Repository rules managed under Settings → Rules & Guidelines are always on: code style, protected directories, review requirements — configure once, injected into every run.

Skills

Skills are capability packs selected explicitly per task (say, "write migration scripts" or "profile performance"). Validated by the JVM, composed by the backend; unselected skills stay out of the prompt budget.

Memories & Commands

Memories keep persistent cross-session facts; Commands provide reusable custom command templates — both managed in their Settings sections.

MCP servers

Connect Model Context Protocol servers under Settings → MCP Servers to extend the agent's tool surface:

  • Supports stdio and HTTP transports, and is compatible with the common MCP config JSON container format (including env / headers expansion and the http alias) — existing configs migrate as-is.
  • Remote servers support OAuth metadata discovery (RFC 9728 / 8414 / OpenID) and RFC 7591 dynamic client registration; discovery failures and missing DCR raise explicit errors instead of silent downgrades.
  • MCP tools obey the same approval and permission rules as built-in tools.

Bring your own keys (BYOK)

Prefer not to route model traffic through the backend's gateway? Bring your own keys. Run these from Search Actions (Ctrl+Shift+A / ⇧+⌘+A):

Anthropic
CodeAgent: Set / Clear Anthropic API Key (BYOK)
OpenAI
CodeAgent: Set / Clear OpenAI API Key (BYOK)
AWS Bedrock
CodeAgent: Set / Clear AWS Bedrock Credentials (BYOK) — credentials, region and model

Keys are written to JetBrains Password Safe, never to plugin config files; the clear actions remove them from Password Safe immediately. The API Keys settings section shows what's currently in effect.

Managed processes

Dev servers and watch builds shouldn't block a conversation turn. CodeAgent runs them in project-scoped managed process sessions:

  • The agent can launch, list, read output from, write stdin to, wait on and kill processes — each operation independently auditable.
  • Process mutations require approval; retained output is capped so memory stays sane.
  • When the project closes, remaining child processes are terminated — no orphans.

Troubleshooting

The panel says the backend is unavailable

  • Local route: make sure the container is running — docker ps should list the backend service at http://127.0.0.1:8788.
  • For the direct dev run (npm start, port 8787), the Backend URL must be overridden in Advanced Settings.
  • Hosted route: check Settings → Services for the real health verdict; a correct URL with an unreachable service is honestly reported as offline.

Indexing is stuck, or the watcher failed

  • Check the repository status chip: when it shows an error, clicking it retries.
  • If it persists, run CodeAgent: Reindex Context for a full rebuild and inspect details with Generate Sync Report.

Node.js not found

The sidecar needs Node.js 22.5+. The plugin probes node and common install locations; with nvm-style multi-version setups, set the executable path explicitly in Advanced Settings.

The panel shows a simplified UI

When JCEF is unavailable the plugin automatically falls back to a Swing UI with a notice; running JCEF out-of-process also triggers a warning. Core conversation features keep working; restore JCEF and restart the IDE for the full interface.

Sign-in state is broken

Sign Out, then Sign In again. Tokens live in Password Safe and plugin settings hold only expiry metadata; removing the entries from your system keychain equals a full sign-out.

Filing a bug report

Run CodeAgent: Export Logs to produce a diagnostic ZIP (including extension status), and submit it with reproduction steps and the failing turn's runId to GitHub Issues.

FAQ

Does my source code get uploaded?

Never wholesale. The index and your source stay on your machine; each run sends only the selected repository context, rules, skills, messages and tool results to the backend you configured. If you deploy that backend yourself, data never leaves your infrastructure.

Does it work offline?

ContextEngine retrieval and indexing are fully local and need no network. Agent turns need a reachable backend — the local Docker backend works in offline environments too, as long as its model endpoint is reachable.

Which IDEs are supported?

Built for the IntelliJ Platform, targeting IDEA, PyCharm, WebStorm, GoLand, CLion, PhpStorm and Rider. Compatibility is checked by JetBrains Plugin Verifier; IDEA and PyCharm are verified on real installs, with the rest in progress.

Will it change code without asking?

No. File writes and terminal commands all pass approval cards, and Ask mode forbids mutations at the capability layer. Per-tool permission rules (deny wins) let you tighten or relax defaults.

Can terminal-command changes be rolled back automatically?

No — and we deliberately don't claim otherwise: the side effects of arbitrary commands can't be safely inferred. File-tool edits have complete rollback paths; for terminal commands, rely on approval review and version control.

Where do model keys live?

Centrally on the backend by default — zero credentials on the IDE side. With BYOK, keys go into JetBrains Password Safe and can be cleared at any time.
